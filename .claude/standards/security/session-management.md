# Session Management

**Framework:** CEF · **Specification:** AS-016 (Security & Compliance Engine) · **Version:** 2.0.0 · **Module:** M-SEC

**Purpose:** Define how an authenticated identity persists across requests. The session is the credential after login — it is stolen, fixed, and replayed exactly as a password is, and it is defended with the same seriousness.

**Language:** MUST / MUST NOT / SHOULD / MAY per RFC 2119.

**Canonical values:** `authentication.policy.yaml` (`session`, `cookies`).

---

## Session Identity

- **SM-01 — Server-validated.** Every session MUST be validated server-side on every request. A client-trusted session — a cookie whose contents the client can forge or alter — MUST NOT be accepted (SP-08).
- **SM-02 — Unpredictable.** Session identifiers MUST be generated by a cryptographically secure random source with sufficient entropy (`authentication.policy.session.identifier_entropy_bits_min`). Sequential, timestamp-derived, or user-derived identifiers MUST NOT be used.
- **SM-03 — Opaque.** A session identifier MUST NOT encode user data, role, or privilege in a form the client can read or modify.

## Fixation

- **SM-04 — Regenerate on privilege change.** The session identifier MUST be regenerated on login, on privilege elevation, and on role change. Reusing a pre-authentication identifier permits session fixation: an attacker plants an identifier, the victim authenticates onto it, and the attacker's session becomes authenticated.
- **SM-05 — Never accept a client-supplied identifier.** A session identifier arriving from a URL, form field, or client header MUST NOT be adopted.
- **SM-06 — No sessions in URLs.** Session identifiers MUST NOT appear in URLs or query strings, where they leak via referrers, logs, history, and shared links.

## Lifetime

Timeout values are canonical in `authentication.policy.yaml`.

- **SM-07 — Idle and absolute timeouts.** Every session MUST carry both an idle timeout and an absolute timeout. An absolute timeout MUST exist so that a stolen session cannot be renewed indefinitely.
- **SM-08 — Shorter for sensitive surfaces.** Administrative and sensitive sessions MUST use the shortened timeouts.
- **SM-09 — Invalidate on credential change.** Logout, password change, password reset, and MFA change MUST invalidate the session. A password reset MUST invalidate *all* sessions and refresh tokens — otherwise the reset does not evict the attacker it was performed to evict.
- **SM-10 — Server-side revocation.** Sessions MUST be revocable server-side. Client-side deletion alone MUST NOT be treated as logout; the server MUST forget the session, because the client's copy may already have been copied.
- **SM-11 — Logout is complete.** Logout MUST clear the session cookie, revoke the server-side session, and revoke associated refresh tokens.

## Cookies

- **SM-12 — `Secure`.** Session cookies MUST set `Secure`; they MUST NOT traverse plaintext.
- **SM-13 — `HttpOnly`.** Session cookies MUST set `HttpOnly` unless JavaScript access is a recorded requirement. Without it, any XSS exfiltrates the session (`xss.md` XSS-11).
- **SM-14 — `SameSite`.** Session cookies MUST set `SameSite`; `Lax` is the minimum and `Strict` is required for sensitive actions (`csrf.md` CSRF-05).
- **SM-15 — Narrow scope.** Cookies MUST be scoped to the narrowest workable path and domain. A cookie scoped to a parent domain is readable by every subdomain, including one an attacker controls.
- **SM-16 — `__Host-` prefix.** The `__Host-` prefix SHOULD be used for session cookies to bind them to the exact origin and prevent subdomain overwriting.
- **SM-17 — Not persistent by default.** Session cookies SHOULD NOT persist beyond the browser session unless "remember me" is an explicit, bounded, revocable feature.

## Storage

- **SM-18 — Not in web storage.** Session material MUST NOT be stored in `localStorage` or `sessionStorage` (`AUTH-15`).
- **SM-19 — Concurrent session visibility.** Users SHOULD be able to see active sessions and revoke them individually. This is the user's only defense against a session they did not create.

## Verification

Cookie flags, storage, and transport MUST be verified on the live response with the **Chrome DevTools MCP** (TE-08). Asserting that flags are set MUST NOT pass the gate.
